# 根据站内访谈更新歌曲评论

适用项目：唯鸡百科 MujicaTimeLineWeb。先确认当前仓库，以下路径均相对仓库根目录，不依赖固定盘符。

## 范围与保留规则

- 默认更新 `_data/data.xlsx` 的 `song_comments` 表。用户俗称 `songs_comment` 时仍以实际表名为准。
- `comment_from` 为 `Remark`、`Tie-up`、`Originally by` 的已有条目不修改、不删除，保留整行内容、样式及链接。
- 其他已有条目可以根据已完成的站内访谈修正译文、署名、日期和来源，也可以补充缺失评论。用户指定歌曲或访谈时只处理该范围。
- 直接摘录站内中文译文，不另译一套、不将原话改成摘要，不修改访谈 Markdown。发现译文本身有问题时单独指出，不暗中更改引用含义。
- 找不到已完成站内来源的旧条目暂时保留，逐条报告。不要凭印象补齐，也不自动抓取或翻译新访谈。
- 默认交付工作簿和变更报告；生成网页或部署按用户要求执行。

## 读取与来源

检查工作区已有改动，读取实际表头。写入前备份当前工作簿到 `_backups/` 下带时间戳的文件，保留用户已有修改。

当前表结构：

| 工作表 | 字段 |
| --- | --- |
| song_comments | song_name、comment_text、comment_source、comment_from、comment_date |
| interview | poster、date、interviewee、title、md_path、if_translated |

从 `interview` 中筛选 `if_translated=yes` 的条目，按 `md_path` 读取 `_data/` 下的 Markdown，并确认实际中文正文完整，无待译占位。标记与正文不一致时暂不使用并报告。

读取 `_data/_docs/md文件翻译规则.md` 确认站内专名和标记；读取歌曲数据与已有评论确认规范曲名、别名和署名。检索时可规范空格、全半角符号和引号，但写回 `song_name` 必须使用实际歌曲关联键。

## 选择与整理评论

1. 检索全部适用访谈的曲名及已确认别名，通读前后问答。不能只搜已有评论涉及的访谈，否则会漏掉后来完成的来源。
2. 区分同名歌曲、乐队、专辑及歌曲改名关系。例如歌曲 `Ave Mujica` 不能与乐队名的泛泛讨论混用。别名对应须由站内数据或正文支持。
3. 收录关于创作、歌词、编曲、录音、演奏、演唱、理解或具体演出感受的实质评论；仅出现歌名、曲目清单或宣发信息不构成评论。
4. 从中文部分摘录能独立理解的连续段落，保留必要提问、发言者及上下文。“这首歌”等指代需明确。不同位置的内容不要拼成貌似连续的原话，必要时分条。
5. 保留站内译文用词、标点和口吻。只清理展示标记，如颜色标签、加粗、图片及原文折叠块；Markdown 链接保留可读文本。不要混入日文原文、图注或元信息。
6. 多人连贯讨论同一首歌时，按对谈整体摘录，保留必要提问、每位发言者及原有接话顺序。署名仅列实际摘录的发言者，不复制访谈全体名单；使用站内规范姓名，多人沿用 `&` 分隔。
7. 用歌曲、来源访谈、发言者和实际段落判断重复，优先更新对应旧条目。同一来源的独立观点可以有多条，不以“歌曲＋作者”简单去重。重复执行不能继续追加相同内容。

## 写入约定

- `song_name`：站内规范歌曲关联键。
- `comment_text`：站内中文摘录。确认 `js/song-modal.js` 当前渲染方式；目前正文会转义 HTML，再把字面量 `\n` 转为换行，因此写入两个字符的 `\n`，不写 HTML `<br>` 或依赖 Markdown 渲染。
- `comment_source`：对应 `interview.title` 的完整原值，供 `InterviewOverlay.hasTitle` 匹配并打开站内访谈。不能只填媒体名、Markdown 文件名或另造标题。
- `comment_from`：使用规范个人姓名、以 `&` 连接的对谈署名，或沿用适用的 `全员` 署名。同一署名下的多条摘录分别写行，复用署名。
- `comment_date`：访谈发布日期，使用 Excel 日期及现有日期格式，不用摘录当天日期。

只修改目标工作表，保留其他表、公式、样式、链接和用户修改，不重建整本工作簿。选择写入工具前检查保存是否会连带改变其他表。

如使用 openpyxl 暂存后替换 XLSX ZIP 中的目标 worksheet XML：通过 workbook 及 relationships 动态定位表，不硬编码 `sheet6.xml`；确保新增单元格只引用有效的既有样式和字符串存储。保留未修改行的 hyperlink 元素及关系，不能复制暂存文件中未同步的关系 ID。复制 ZIP 条目时复制 `ZipInfo`，避免写入改变原对象偏移而影响读取。先在临时文件校验再替换工作簿。

## 歌曲弹窗的标签归组与顺序

每次更新时，用受影响歌曲的全部评论核对 `js/song-modal.js` 的实际归组与排序，并在变更报告中记录校验结果。

- 每条记录只进入一个标签。个人按姓名归组，`全员` 独立归组，对谈按完整参与者组合归组。同一组合的署名次序互换仍共用一个标签。例如“冈田梦以”“冈田梦以 × 米泽茜”“冈田梦以 × 佐佐木李子”各自独立。
- 标签内按访谈日期从早到晚展示，同日沿用表中顺序。每条摘录分别保留日期、完整正文和可追溯的出处。
- 标签依次为说明项（`Remark`、`Tie-up`、`Originally by`）→ 全员 → 成员个人（佐佐木李子 → 渡濑结月 → 冈田梦以 → 米泽茜 → 高尾奏音）→ 其他个人（如 Diggy-MO'、柿本广大）→ 对谈。只展示有记录的标签，说明项、其他个人和对谈各自在同类中沿用首次出现的顺序。

## 校验与交付

- 重新打开工作簿，核对全部新增／修改行的曲名有效、日期正确、来源标题唯一匹配、正文有对应已译段落。
- 对比备份确认三类受保护条目完整不变，其他工作表未改变。仅替换 worksheet XML 时应验证其他 ZIP 条目内容完全一致。
- 检查重复、乱码、翻译占位、残余颜色标签和日文折叠内容。摘录必须可追溯至具体文件与段落，而非仅验证关键词存在。
- 在 `_reports/` 保存带时间戳的变更清单，记录动作、歌曲、作者、来源文件及段落位置，以及保留项和实际原因。
- 报告更新数、新增数、涉及歌曲数及受保护条目数。对保留旧评论逐条列出歌曲、作者、原来源及原因，区分“来源未收录”“已收录但未译”“出处疑似不匹配”，不能统称未翻译。数量由当次数据计算。

除非用户要求删除，来源疑似错误的旧条目也先保留并说明。再次运行时重新核对来源状态，不将历史待核对清单当成永久排除名单。
